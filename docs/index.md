## Go

### GMP模型

| 角色 | 全称 | 含义 | 核心职责 |
| --- | --- | --- | --- |
| **G** | Goroutine | 协程 | 待执行的任务，用户态轻量级线程，初始栈仅 2KB，按需动态扩容 |
| **M** | Machine | 系统线程 | 真正执行代码的操作系统内核线程，由 OS 内核调度 |
| **P** | Processor | 逻辑处理器 | 包含调度 G 所需的上下文和本地队列，数量通常等于 CPU 核心数（`GOMAXPROCS`） |

首先，GMP中的G是用户态的协程，具备完整的栈信息，初始仅2KB，可动态扩容。M是操作系统的线程，由内核调度。P是调度G的逻辑处理器，M 必须绑定一个 P 才能执行代码。
在Go早期，只有GM模型，这导致全局锁竞争激烈，在加入了P之后，就分为了本地队列和全局队列，当创建新的 Goroutine 时，会优先放入本地队列，如果本地队列已满，则取本地队列的一半放入全局队列，避免频繁的全局锁竞争。
如果本地队列为空，则会依次从全局队列、网络轮询器、其他队列窃取任务（全局队列根据M数量窃取，其他队列窃取一半），同时为了避免全局队列的饥饿，本地队列会在每61次调度从全局队列取一个任务。
当G进行阻塞性的系统调用（如阻塞读写磁盘或网络），正在运行它的M会同G一起陷入阻塞状态，此时会把P剥离出来，转交给其他空闲的M。当系统调用结束后，原来的M会尝试重新绑定空闲的P，如果抢不到P，就把当前的G放入全局队列，自己转入休眠。
对于普通的网络I/O（Go封装的非阻塞网络调用），M不会被阻塞，而是会挂载netpoller，M直接执行其他G，数据就绪后再唤醒G。
另外，Go的调度之前是协作式，这导致了某些G可能一直占用M而不会释放，现在已经改为了抢占式，运行超过一定时间会强制中断M的执行。

### GC

GC的演变一直在优化STW导致的停顿问题。Go的GC最早是标记-清除算法，整个过程都需要STW，导致程序严重的卡顿；之后引入了并发三色标记和插入写屏障，标记协程可以和用户协程并发执行，显著降低了STW的停顿，由于栈的操作非常频繁，因此在栈上不开启插入写屏障，这导致了标记结束后需要STW再次对栈扫描，确认标记期间的修改；最后引入了混合写屏障，写屏障只作用于堆，栈上全黑且栈上新建对象直接标黑，而堆上对象引用的插入和删除时标记为灰色，避免了栈的STW二次扫描，因此进一步降低STW导致的停顿。

GC的过程是这样的，
1. 标记开始时，开启写屏障，短暂的STW
2. 并发标记，GC协程与用户协程并发执行，GC协程从根对象开始，初始对象都是白色，已完全扫描的对象是黑色，部分扫描的对象是灰色。
3. 标记结束时，关闭写屏障，短暂的STW
4. 并发清理，回收所有标记为白色的对象，该过程没有STW

GC 会在内存达到阈值和超过2分钟没有GC时被触发。在实际的业务中，通过`sync.Pool`复用对象、预分配容量避免slice/map频繁扩容、减少变量逃逸（小对象优先传值而非指针）等方式来降低GC压力。

!!! note "协助标记"

    Go 默认分配 25% 的 CPU 用于后台 GC 标记。如果某个协程分配内存过快（超出后台标记速率），运行时会强制该协程暂停业务代码，转而**协助进行三色标记**。这样既压制了该协程分配新内存的速度，又借用其 CPU 算力加速了标记的完成。

## 分布式系统

### 分布式系统如何保证数据的一致性？

分布式系统下由于网络分区不可避免，根据 **CAP / BASE 理论**，绝大多数互联网业务都会选择**牺牲强一致性、追求高可用**，采用**最终一致性（柔性事务）**；而在注册中心、元数据、分布式协调等场景则追求**强一致性（刚性事务/共识）**。我将从最终一致性和强一致性两方面展开：

#### 1. 最终一致性（柔性事务，业务系统主流）
- **可靠消息最终一致性（本地消息表 / RocketMQ 事务消息，最推荐）**：
  - **RocketMQ 事务消息**：利用“半消息（Half Message）+ 本地事务状态回查”机制，保证本地 DB 操作与消息发送的原子性。
  - **本地消息表（Outbox Pattern）**：将业务数据变更和消息记录在**同一个本地数据库事务**中提交，后台定时任务或通过 CDC（Canal 监听 Binlog）抓取消息投递到 MQ。
  - **下游保障**：下游消费失败自动重试，必须实现**接口幂等性**（基于唯一业务流水号或防重表），极端失败进入死信队列（DLQ）。
- **TCC 补偿型事务（针对强业务约束场景，如跨境转账、资产冻结）**：
  - 分为 **Try**（资源预留/冻结，如冻结 100 元）、**Confirm**（确认扣除）、**Cancel**（释放预留资源）。
  - 不依赖底层数据库锁，性能优于 2PC，但**业务侵入性高**（每个微服务需手写 3 个接口），且必须妥善处理**幂等、空回滚、防悬挂**三大难题。
- **Saga 模式（适用于长业务链，如电商下单出库、旅游出行套票）**：
  - 将一个分布式事务拆解为多个子事务 $T_1, T_2, \dots, T_n$。若某一步失败，按反向顺序依次调用对应的补偿事务 $C_{n-1}, \dots, C_1$。可通过状态机中心化编排（Orchestration）实现。

#### 2. 强一致性（刚性事务 / 基础组件）
- **共识算法（Raft / Paxos）**：
  - 应用于 etcd、ZooKeeper、TiKV 等分布式协调与分布式存储系统中。通过 Leader 选举 + 多数派（Quorum）日志复制确认，在节点故障时仍能对外提供强一致的读写。
- **2PC / 3PC（两阶段/三阶段提交，XA 协议）**：
  - 依赖全局事务协调者（Coordinator），经历准备（Prepare）和提交（Commit）两阶段。缺点在于同步阻塞、协调者单点故障、性能极差，目前仅在单库跨表或传统金融内部极小范围使用。

#### 3. 最终兜底闭环（工程落地核心）
- **唯一流水号与全链路幂等**：所有跨服务操作强依赖全局唯一 `tx_id / order_no`，消费端通过 Redis SetNX 或 DB 唯一索引防止重复执行。
- **对账系统与人工兜底**：任何分布式事务机制都不能保证绝对零差错。线上配合**定时对账任务（T+1 或准实时）**对比上下游流水差额，不一致时自动补偿修复，无法自动处理的触发高优先级报警交由人工对账补偿。

### 分布式事务如何实现？

单机事务依赖数据库原生的 ACID（Undo/Redo Log 和锁机制），微服务拆分后跨进程、跨库，本地事务失效。实现分布式事务主要有以下四种工业界主流方案，核心是根据**业务场景、性能要求和侵入性**做权衡：

#### 1. 四大主流实现模式
- **MQ 事务消息 / 本地消息表（异步最终一致性，首选方案）**：
  - **原理**：基于 RocketMQ 事务消息（Half 消息 + 本地事务回查）或本地消息表（业务与消息在同一本地事务提交 + 定时投递）。下游服务监听消息消费入库，失败不断重试。
  - **适用**：绝大多数允许异步解耦的非实时场景（如支付成功后发货、加积分、发短信）。
- **Seata AT 模式（无侵入二阶段提交）**：
  - **原理**：第一阶段业务 SQL 执行时，框架自动解析 SQL 生成前镜像（Before Image）和后镜像（After Image）存入 `undo_log` 表，随本地事务一同提交并快速释放本地行锁；第二阶段若成功则异步清理 undo log，若失败则通过前镜像数据反向生成回滚 SQL 还原数据。
  - **适用**：老系统改造、单体拆微服务、希望**零业务代码侵入**的企业级系统。
- **TCC 模式（业务层两阶段提交，高并发强约束）**：
  - **原理**：将业务拆解为 **Try**（资源冻结/预留）、**Confirm**（真正扣除已冻结资源）、**Cancel**（释放冻结资源）。由于只在 Try 阶段冻结局部资源（如将余额拆出冻结字段），不长期占用底层 DB 行锁，性能极高。
  - **适用**：核心高并发交易、热点资金/库存账户扣减。
- **Saga 模式（长事务编排）**：
  - **原理**：将大长事务拆分为多个独立的子事务 $T_1, T_2, \dots, T_n$ 并发/串行执行；某一步失败时，状态机协调器（Orchestrator）反向依次回滚调用补偿接口 $C_{n-1}, \dots, C_1$。
  - **适用**：跨部门/跨第三方外部系统调用（如调用微信支付、航司订票接口，无法做 TCC 的场景）、长周期业务流程。

#### 2. 面试必问三大深水区（TCC / 柔性事务踩坑与解决）
1. **空回滚（Null Rollback）**：
   - **原因**：分支事务的 Try 请求因网络丢包或拥堵尚未到达，事务管理器判定超时直接触发了 Cancel。
   - **解决**：Cancel 接口执行前必须先查询分支事务日志。如果发现 Try 未执行，仅记录一条“空回滚标记”，绝不执行回滚业务逻辑。
2. **防悬挂（Suspension）**：
   - **原因**：Cancel 执行完毕后，之前迟到的 Try 请求才到达目标服务并成功执行，导致预留资源被永久冻结，无法释放。
   - **解决**：Try 接口执行前必须先检查该事务是否已被记录为“已回滚/空回滚”，若是则直接拒绝执行。
3. **幂等性（Idempotency）**：
   - **原因**：网络超时引发协调器自动重试 Try、Confirm 或 Cancel。
   - **解决**：每个分支接口基于全局 `tx_id + branch_id` 记录状态流水，重复请求直接返回成功。

#### 3. 选型总结（面试一句话收尾）
> “在实际业务中，**90% 的场景优先选 MQ 事务消息**（性能最高、改造成本最低）；核心高并发账户与库存选 **TCC**；无代码侵入的内部微服务系统选 **Seata AT**；涉及外部三方调用与超长跨系统链路选 **Saga**。”


### 秒杀系统怎么设计？（核心：防超卖与高可用）

秒杀系统本质是应对读极大、写极集中的瞬时极端流量超高并发场景，核心痛点就是绝不能超卖和必须保住系统高可用。整体架构遵循**『漏斗模型』**：通过动静分离、分层过滤、缓存扣减与异步削峰，层层拦截流量。在设计上我会重点围绕这两条核心主线展开：

#### 1. 如何彻底杜绝超卖（库存一致性）
- **库存预热与 Redis 原子扣减**：活动前将库存预热至 Redis。扣减逻辑通过 **Lua 脚本**把「校验用户限购 -> 校验库存 -> 扣减库存 -> 记录已买用户」打包成原子操作，在内存层毫秒级拦截 99% 的无效流量。
- **防重复下单（幂等）**：在 Redis 中用 Set 存储已购买的 UID；数据库订单表将 `user_id + activity_id` 设为唯一索引，即便用户重试或并发穿透，也能保证一人只能下一单。
- **DB 条件更新最终兜底**：下游异步入库扣减 DB 真实库存时，采用带版本或条件约束的更新（`UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0`），依靠行锁保证 DB 绝对不会扣成负数。
- **超时未支付库存回补**：利用 RocketMQ 延迟消息或 Redis 键过期监听支付状态，如果 15 分钟未支付则自动关闭订单、回退 DB 库存，并通过 Lua 脚本回补 Redis 缓存。

#### 2. 如何保障系统高可用（流量治理与削峰）
- **动静分离与端侧防刷**：商品详情页等静态资源推至 CDN；秒杀按钮防抖并结合验证码/算术题拉长并发请求区间；秒杀接口 URL 动态化（加盐 Hash，活动开启后才下发动态 Token），防止黑产逆向提前刷接口。
- **网关层限流（分层阻断）**：在 API 网关基于令牌桶/漏桶算法，对单 IP、单 UID 以及整体集群做阈值限流，超出压测水位的请求秒级快速失败，返回“排队中”友好提示。
- **MQ 异步削峰**：Redis 扣减成功即向用户返回“抢购成功，排队出单中”，后台向消息队列投递下单消息，订单/支付服务根据 DB 承载上限平滑消费入库，避免数据库连接池被瞬时打爆。
- **物理隔离与熔断降级**：秒杀的域名、网关、服务集群、Redis 及 DB 均与日常主业务做物理隔离，避免秒杀异常影响全站；非核心依赖（如积分、推荐、消息推送）全面做降级或异步化，保障核心下单链路绝对存活。

### 如何解决长对话摘要丢失关键信息？

单纯全局摘要很容易丢失用户早期核心需求、硬性偏好这类关键信息，我会四层机制组合规避：

1. 先用工作内存把用户固定目标、输出约束单独隔离常驻提示词，完全不参与摘要压缩，守住底线；
2. 不做一次性全局总结，采用分段增量摘要，给每段内容打上优先级与时序标签，避免抹平早期关键信息；
3. 底层搭配RAG语义检索向量库，摘要只做提纲，完整原始对话永久存储，遗漏细节可随时召回原文；
4. 针对超长会话、大量工具返回的复杂场景，上 Multi-Agent Memory：主对话 Agent 只负责交互，Observer / Reflector / Retriever 专职写记忆、评优先级、按需召回，用分工替代全文压缩，从架构上避免关键信息丢失与上下文膨胀。
